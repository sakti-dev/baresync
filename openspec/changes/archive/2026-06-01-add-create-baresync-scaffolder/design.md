## Context

Baresync has a manual onboarding path that asks users to create a workspace, run official Tauri and Hono CLIs, create a sync-contract package, wire server routes, configure local and server migrations, and register the Tauri plugin. The official app CLIs are best left in charge of their own boilerplate, but Baresync-specific project structure and sync wiring are stable enough to scaffold.

This change is planned after `simplify-tauri-plugin-registration`. The scaffolder should target the simplified plugin builder API with plugin-owned commands and generated contract metadata, not the current long command-wrapper setup.

## Goals / Non-Goals

**Goals:**

- Provide a create-style CLI for `bun create baresync` and comparable npm/pnpm/yarn create flows.
- Proxy official Tauri and Hono/Elysia CLIs interactively instead of copying their templates.
- Generate a default todo sync-contract package with `lists` and `todos`.
- Generate Baresync-specific server route modules and Tauri helper modules.
- Generate Drizzle migration configs and scripts, while leaving SQL migration files to `drizzle-kit generate`.
- Keep frontend UI integration framework-neutral.

**Non-Goals:**

- Do not replace official Tauri, Hono, or Elysia scaffolding.
- Do not generate SQL migration files directly.
- Do not mount React/Solid/Svelte providers or modify UI component trees.
- Do not add inventory or blank template variants in the first version.
- Do not support every server deployment target in v1; start with local Bun + SQLite scaffolding.

## Decisions

### Separate Create Package

Add a create-focused package such as `create-baresync` instead of adding project creation to the existing `baresync` binary. The existing `baresync` package remains the library and generator/doctor CLI; the create package owns prompts, templates, CLI proxying, and post-processing.

Alternative considered: add `baresync create`. That makes local development easy but does not match `bun create baresync` conventions as cleanly and would add scaffolder dependencies to the runtime package.

### Proxy Official App CLIs

The scaffolder will use `child_process.spawn` with `stdio: "inherit"` for official Tauri and server CLIs. This preserves native prompts and lets upstream projects maintain their boilerplate.

Alternative considered: copy local Tauri/Hono/Elysia templates. That would reduce prompt complexity but create long-term maintenance work and stale framework templates.

### Todo Sync-Contract Template

The default sync-contract template uses `lists` and `todos`. It is small enough for new users while still demonstrating scope columns, local versus API sync columns, foreign-key ordering, runtime tables, and generated sync artifacts.

Alternative considered: use the inventory example as the default. Inventory is a useful reference but too domain-specific for first-run scaffolding.

### Generate Source, Not SQL Migrations

The scaffolder will generate Drizzle schemas and Drizzle config files, then provide scripts for users to generate local and server migrations. SQL migration files remain generated by `drizzle-kit` from schema source.

Alternative considered: copy static SQL migrations. That would make the first run feel complete but risks stale migrations as soon as the template schema changes and undermines the docs' schema-first workflow.

### Separate Server Route Modules

For Hono and Elysia, the scaffolder generates Baresync server integration in separate route/module files and performs a minimal mount patch in recognized entrypoints. If the entrypoint cannot be safely patched, it still writes the route files and prints manual mount instructions.

Alternative considered: overwrite the server entrypoint. That is simpler but discards official CLI output and risks damaging user-selected template details.

### Tauri Source Patching Stays Minimal

The scaffolder generates Tauri helper modules and compact plugin setup, then patches only predictable `src-tauri` files. It does not modify frontend UI entrypoints beyond adding framework-neutral helper modules such as a Drizzle DB module and sync client module.

Alternative considered: mount providers or UI examples automatically. This is brittle because Tauri templates can use different frontend frameworks and app structures.

## Risks / Trade-offs

- [Official CLI prompts produce unexpected project shapes] -> Detect known shapes before patching; fall back to generated files plus manual instructions.
- [Package manager create semantics differ] -> Detect `npm_config_user_agent`, support direct Bun runtime fallback, and keep command construction isolated behind package-manager adapters.
- [Server runtime choices do not match Bun + SQLite templates] -> Scope v1 post-processing to compatible local Bun server output and clearly document unsupported shapes.
- [Scaffolded project depends on a prior plugin-registration change] -> Implement this change after `simplify-tauri-plugin-registration` or keep tasks blocked until that API exists.
- [Generated files drift from docs] -> Add snapshot/content tests for template output and update getting-started docs from the same intended file layout.

## Migration Plan

1. Land `simplify-tauri-plugin-registration`.
2. Add `create-baresync` as a workspace package with templates and CLI entrypoint.
3. Implement package-manager detection and interactive proxy helpers.
4. Add todo sync-contract, server, Tauri, and Drizzle config templates.
5. Add conservative patchers for Hono/Elysia and Tauri files.
6. Update docs to present create flow first and manual setup as fallback.

Rollback is to leave manual setup docs and the existing `baresync` CLI unchanged. The create package can be unpublished or omitted from release without affecting the core library.

## Open Questions

- Should the first release support Elysia immediately, or should Elysia be generated as route files without automatic entrypoint patching?
- Should the scaffolder ask before running final `install` and generation commands, or only print next steps in v1?

## ADDED Requirements

### Requirement: Public fixture uses generated protobuf transport

The public fixture Tauri app SHALL use the same generated protobuf transport pattern documented for consumers when running in protobuf mode.

Fixture protobuf mode SHALL NOT depend on a bespoke hand-written transport that is unavailable to consumers unless that code is generated by the same generator template used for public protobuf output.

#### Scenario: Fixture protobuf wiring matches public pattern

- **WHEN** the fixture app is built in protobuf transport mode
- **THEN** it SHALL import generated Rust protobuf output
- **AND** it SHALL pass the generated protobuf transport to `tauri-plugin-baresync`
- **AND** it SHALL register the plugin through the same public builder surface expected of consumers

#### Scenario: Fixture no longer owns private protobuf transport logic

- **WHEN** maintainers inspect the fixture app protobuf transport path
- **THEN** protobuf encoding, decoding, and row mapping logic SHALL come from generated code or the generator template under test
- **AND** the fixture app SHALL NOT contain a separate one-off protobuf transport implementation that users cannot generate

### Requirement: Protobuf smoke validates real plugin transport

The public fixture smoke scenario SHALL prove that protobuf mode sends real protobuf sync traffic through the Tauri plugin boundary.

#### Scenario: Desktop protobuf smoke sends protobuf

- **WHEN** the desktop fixture smoke runs in protobuf mode
- **THEN** baseline pull, local create, manual sync, backend state assertion, and restart persistence SHALL pass
- **AND** the backend or captured request evidence SHALL show sync requests using `Content-Type: application/x-protobuf`

#### Scenario: Android protobuf smoke sends protobuf

- **WHEN** the Android fixture smoke runs in protobuf mode on a connected adb target
- **THEN** baseline pull, local create, manual sync, backend state assertion, and restart persistence SHALL pass
- **AND** the backend or captured request evidence SHALL show sync requests using `Content-Type: application/x-protobuf`

#### Scenario: JSON and protobuf smoke remain equivalent

- **WHEN** the same fixture smoke scenario runs in JSON mode and protobuf mode
- **THEN** user-visible synced data, pushed backend state, local clean-state indicators, and restart persistence SHALL satisfy the same assertions

### Requirement: Protobuf smoke evidence

The fixture smoke harness SHALL collect or print enough evidence to distinguish protobuf transport failure from server, database, or UI failure.

#### Scenario: Protobuf failure evidence includes transport mode

- **WHEN** a protobuf fixture smoke run fails
- **THEN** failure evidence SHALL include selected transport mode, app-visible transport mode, backend transport mode, sync endpoint request evidence when available, and generated artifact freshness command guidance

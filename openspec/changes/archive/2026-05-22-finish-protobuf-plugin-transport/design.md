## Context

Baresync currently has protobuf support in the generator and TypeScript server boundary, but the Rust app runtime path is incomplete. `baresync-core` builds logical sync envelopes as `serde_json::Value`, `JsonHttpTransport` is the default HTTP transport, and `tauri-plugin-baresync` stores `encoding` without using it to select a protobuf transport. The fixture app has a hand-written `FixtureProtobufTransport`, which proves the approach but is not a public library feature.

The missing product behavior is straightforward: a consumer Tauri app should be able to generate protobuf artifacts, import generated Rust transport code, configure the plugin, and send protobuf sync traffic to a protobuf-aware server. This must remain schema-specific because protobuf row messages and table envelope fields are generated from the user's sync contract.

## Goals / Non-Goals

**Goals:**
- Make protobuf a complete public app sync path for Tauri consumers.
- Generate schema-specific Rust code that implements `SyncHttpTransport` for protobuf push, pull, and status requests.
- Keep the core engine's sync orchestration and local database behavior unchanged.
- Require explicit protobuf transport wiring so `.encoding("protobuf")` cannot silently use `JsonHttpTransport`.
- Reuse the same generated protobuf message definitions for Rust transport, fixture app smoke tests, and public examples.
- Verify protobuf mode with real plugin traffic, not only TypeScript server encode/decode tests.
- Update public docs so users understand the exact server, generator, and plugin wiring required.

**Non-Goals:**
- Do not make protobuf the default encoding.
- Do not replace the engine's internal `serde_json::Value` logical envelope model in this change.
- Do not build a generic runtime-reflection protobuf encoder in Rust.
- Do not require protobuf for JSON users or change the JSON transport path.
- Do not make device smoke tests mandatory for normal fast verification.

## Decisions

### Generate a schema-specific Rust transport

The protobuf transport SHALL be generated from the sync contract because table row messages, field numbers, and per-table envelope fields are schema-specific. The generated Rust runtime should expose prost message structs, logical `serde_json::Value` mappers, and a transport type or factory, for example `GeneratedProtobufTransport` or `baresync_protobuf_transport()`.

**Alternative considered:** Add one generic `ProtobufHttpTransport` to `baresync-core`. Rejected because the core crate does not know the user's generated row types or table fields.

### Keep core sync logic JSON-shaped internally

The engine should continue to build push, pull, and status bodies as logical `serde_json::Value` objects. The generated transport becomes the codec boundary: it maps logical values to generated prost request messages, sends `application/x-protobuf`, decodes generated prost response messages, and maps responses back to logical values.

This minimizes risk because chunking, local outbox, cursor handling, server-wins reconciliation, and SQLite application logic stay in the already-tested engine path.

**Alternative considered:** Refactor the engine to be generic over typed protobuf request/response structs. Rejected for this change because it would touch unrelated engine semantics and make JSON/protobuf behavior easier to drift.

### Require explicit protobuf transport wiring

The plugin builder should treat `encoding: "protobuf"` without an explicit transport as invalid or at least fail during setup with an actionable error. This closes the misleading path where user code appears to enable protobuf but still sends JSON.

The public pattern should be explicit:

```rust
mod protobuf_generated;

BaresyncBuilder::new()
    .encoding("protobuf")
    .transport(protobuf_generated::baresync_protobuf_transport())
```

**Alternative considered:** Let `.encoding("protobuf")` automatically select protobuf. Rejected for now because the plugin cannot construct a schema-specific generated transport unless the app imports generated code.

### Replace fixture-only protobuf transport with generated transport

The fixture app should stop owning a bespoke `FixtureProtobufTransport` that users cannot copy from package output. It should use the generated transport path, or code generated by the same generator template, so fixture E2E validates the public integration model.

**Alternative considered:** Keep fixture transport as an internal proof. Rejected because it would allow tests to pass while external users still lack a supported path.

### Verify protobuf at the HTTP boundary

Tests should assert more than logical parity. Contract and smoke paths should prove protobuf mode sends protobuf content types and binary bodies where observable, and that the same baseline pull, local create, push, and restart behavior passes through the public plugin wiring.

**Alternative considered:** Only test encode/decode helpers. Rejected because that is exactly the gap this change is closing.

## Risks / Trade-offs

- [Risk] Generated Rust transport becomes large and schema-specific. Mitigation: keep it deterministic, generated, and committed like the existing protobuf artifacts.
- [Risk] Users configure `encoding: "protobuf"` but pass the JSON default transport manually. Mitigation: fail when no explicit transport is provided, document the generated transport import, and add integration tests around the recommended path.
- [Risk] Mapping between `serde_json::Value` and prost structs mishandles nullable fields, booleans, bytes, or int64 values. Mitigation: generator tests and fixture E2E SHALL cover round-trips for supported scalar mappings and deleted/null values.
- [Risk] Protobuf smoke tests become slow or flaky. Mitigation: keep host/backend contract tests as the required fast gate and keep desktop/Android smoke opt-in, matching existing E2E policy.
- [Risk] Public docs overstate protobuf support again. Mitigation: docs SHALL distinguish required generator, server, and plugin transport wiring, and examples SHALL include the generated transport setup.

## Migration Plan

1. Add generated Rust transport output while preserving existing protobuf generation entrypoints.
2. Update fixture generated artifacts and replace bespoke fixture transport code with generated transport usage.
3. Add builder validation so protobuf encoding without explicit transport fails with an actionable error.
4. Update docs to show protobuf as a complete flow only when generated transport is wired.
5. Keep JSON users unaffected; existing JSON configs and examples continue to use the default transport.

Rollback is straightforward: keep the generated prost structs and TS protobuf server path, remove the generated Rust transport and builder validation, and document protobuf as server-side/artifact support only. This rollback would intentionally restore protobuf to partial status.

## Open Questions

- Should the generated transport live in the existing `rustSyncMappers` output file, or should the protobuf config add a separate `rustTransport` output path?
- Should the generated public factory return `Arc<dyn SyncHttpTransport>` directly, or expose a concrete transport type plus helper factory?
- Should `Builder::encoding("protobuf")` fail at `.build()` time or during plugin setup when no explicit transport is configured?

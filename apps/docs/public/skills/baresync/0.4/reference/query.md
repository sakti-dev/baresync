## What is baresync?

A local-first sync system for Tauri apps. Your app reads/writes SQLite directly. Changes sync to your own backend via a polling-based push/pull mechanism.

## How does sync work?

```
App writes to SQLite → outbox entry (atomic) → plugin polls every N seconds
→ POST outbox entries to /push → POST last cursor to /pull
→ apply pulled rows to local DB → emit Tauri events → React Query invalidates
```

## What is the outbox pattern?

Every syncable write atomically performs two things:

1. The mutation (insert/update/soft-delete)
2. An outbox entry recording what changed

If network is down, outbox entries wait. When connectivity returns, the sync engine pushes pending changes. Writes never fail due to connectivity.

## What are paired schemas?

Every synced table has two Drizzle schema definitions:

- **Local** (`localSyncColumns()`) — has `isSynced` boolean, `deletedAt`, `createdAt`, `updatedAt`
- **API** (`apiSyncColumns()`) — has `syncUpdatedAt` integer cursor, `deletedAt`, `createdAt`, `updatedAt`

Same table name, same business columns, different sync metadata. The sync contract is the shared truth.

## What is the sync contract?

A JSON file generated by `bun run generate:sync` from `sync.config.ts`. Contains table definitions, column mappings, and upsert order. The Tauri plugin embeds it at compile time via `include_str!`.

## How does conflict resolution work?

**Server wins.** When the same row changes on both client and server, the server state overwrites local during pull. No configurable conflict resolution.

## What is a scope?

Every synced row belongs to a scope (tenant, workspace, merchant). Your server's `resolveScope` function checks that the requesting user has access to the requested scope. The contract defines which column is the scope column.

## How does pull work incrementally?

The local database stores a cursor timestamp per scope. The server returns only rows changed after that cursor. After applying pulled rows, the cursor advances to the latest `syncUpdatedAt` from the response.

## What are soft deletes?

Deleted rows get a `deletedAt` timestamp and `isSynced: false`. The sync engine pushes this as an update so the server can mark the row as deleted. **Never use hard deletes** (`.delete()`) on synced rows — they won't be tracked.

## What does `writeLocalChange` do?

Opens a Drizzle transaction and atomically:

1. Runs your `write` callback (the actual insert/update)
2. Inserts a row into `sync_outbox` with table name, row ID, and operation

The `sync_outbox` has a unique partial index on `(table_name, row_id) WHERE synced_at IS NULL`. The code does a plain `INSERT` — if a pending entry already exists for the same row, the unique index causes a constraint violation. Handle this by catching the error or checking for existing pending entries before inserting.

## Why two schema files?

The server and client have different sync metadata needs:

- Server tracks sync state with an integer `syncUpdatedAt` cursor (used for incremental pull)
- Client tracks sync state with a boolean `isSynced` flag (used to know what needs pushing)

Business columns are identical. Only the sync metadata columns differ.

## How does the plugin communicate with JS?

The Tauri plugin:

1. Opens/manages the SQLite database
2. Runs the sync engine on a polling interval
3. Emits Tauri events (`baresync://data-changed`, `baresync://sync-status-changed`)
4. Exposes commands that JS calls via `invoke`

The TypeScript client (`baresync/db`) wraps these into a Drizzle proxy and sync client.

If the exact implementation details matter, load `reference/source.md` and read the mapped workspace file.

## What does `enqueueChange` do?

Records an outbox entry without performing the write itself. Use when the mutation is already done (e.g., bulk update via `.returning()`) and you only need outbox tracking.

## How are generated schemas frozen?

Each generation creates a date-stamped directory (`generated/<YYYY-MM-DD>/`). The server imports from this frozen snapshot. Editing source files after generation doesn't change the generated copies — you must regenerate to pick up changes. This ensures the server and plugin always use a versioned, immutable contract.

## What sync modes exist?

When you call `sync_now`, the engine inspects local and server state and picks one of five modes:

| Mode | When | What happens |
|---|---|---|
| `no_op` | Both sides up to date | Nothing |
| `push_only` | Local writes pending, no server changes | Push outbox → GC |
| `pull_only` | No local writes, server has changes | Pull changes → apply → GC |
| `full_sync` | Both sides have changes | Pull first (minimize rejections) → push → re-pull rejected → GC |
| `full_resync` | First sync or explicit request | Baseline pull (empty cursor) → push → GC |

The resolved mode is in the result:

```ts
const result = await client.syncNow({ scopeId: "merchant-1" });
// result.mode → "no_op" | "push_only" | "pull_only" | "full_sync" | "full_resync"
```

Use this to drive UI state — e.g. show a spinner only when mode is not `no_op`.

## When should I use sync_full_resync instead of sync_now?

`sync_now` auto-selects the best mode. Use `sync_full_resync` when:

- First sync on a new device (forces baseline pull even if a stale cursor exists)
- After a server migration that changes data shape
- When data seems corrupted and you want a clean slate

`sync_full_resync` starts from an empty cursor, pulls everything, then pushes local outbox. It does not check status first.

## Is data available immediately after a write?

Yes. On the client side, Baresync uses a single SQLite connection with WAL mode. Reads after a committed write always see the new data — you don't need to wait for an event or a sync cycle.

## What's the difference between push, pull, syncNow, and fullResync?

| Command | Pushes? | Pulls? | Use when |
|---|---|---|---|
| `syncNow()` | Yes | Yes | General use — auto-selects best mode |
| `push()` | Yes | No | Guarantee local writes sent before navigating away |
| `pull()` | No | Yes | Server has new data, want it immediately (e.g. after push notification) |
| `fullResync()` | Yes | Yes | Clean slate — corrupted data, long offline, debugging |

`syncNow` is the right default. Use `push`/`pull` only when you need one direction specifically.

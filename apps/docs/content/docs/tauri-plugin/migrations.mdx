# Migrations

The plugin applies SQL migrations at startup, before any JS code runs. You can either ship `.sql` files as Tauri resources with `migrations_path(...)` or embed the SQL into the binary with `migrations(...)`.

## Path-based migrations

Path-based migrations are the simplest production-ready setup. Put your `.sql` files in a `migrations/` directory, bundle them with Tauri, and point the builder at that folder:

```rust
builder.migrations_path("migrations")
```

Relative paths are resolved from the Tauri resource directory during plugin setup. Add the files to your Tauri bundle resources so they are available in production:

```json
{
  "bundle": {
    "resources": ["migrations/*.sql"]
  }
}
```

This reads all `.sql` files from the `migrations/` directory, sorted by filename:

```txt
migrations/
├── 0001_init.sql
├── 0002_add_items.sql
└── 0003_add_stock_counts.sql
```

Files are sorted by filename and applied in order. Only `.sql` files are included.

### Statement breakpoints

Split multiple statements within a single migration using `--> statement-breakpoint`:

```sql
CREATE TABLE locations (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL
);
--> statement-breakpoint
CREATE TABLE items (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  location_id TEXT NOT NULL
);
```

Each segment is executed as a separate statement within a single transaction.

## Migration execution

Migrations run in **strict mode** by default:

- Each migration runs in a transaction
- If any statement fails, the entire migration rolls back
- Already-applied migrations are skipped (tracked by hash in `__drizzle_migrations`)

The plugin calls `run_migrations` during setup, so migrations are applied before your JS code loads. It uses either the configured path-based migrations or the embedded migrations, depending on how you set up the builder.

## Migration tracking

Applied migrations are recorded in `__drizzle_migrations`:

| Column | Type | Description |
|---|---|---|
| `id` | `INTEGER` | Auto-increment primary key |
| `hash` | `TEXT` | Migration name (unique) |
| `created_at` | `INTEGER` | Unix timestamp in milliseconds |

Check migration status from JS:

```ts
const status = await invoke("plugin:baresync|get_migration_status");
```

## Adding a new migration

1. Create `migrations/0004_add_column.sql` with the new SQL
2. Rebuild — the build script picks it up automatically
3. The plugin applies it on next launch

## Embedded migrations

Embedded migrations are the advanced option when you want the SQL compiled into the binary instead of shipped as files.

```rust
use baresync_core::migrations::EmbeddedMigration;

let migrations = vec![
    EmbeddedMigration {
        name: "0001_create_items",
        sql: "CREATE TABLE items (
            id TEXT PRIMARY KEY,
            name TEXT NOT NULL,
            scope_id TEXT NOT NULL,
            deleted_at TEXT,
            is_synced INTEGER NOT NULL DEFAULT 0,
            created_at TEXT NOT NULL,
            updated_at TEXT NOT NULL
        )",
    },
];

builder.migrations(migrations)
```

### Where the SQL comes from

In practice, you generate these from your Baresync sync contract:

```bash
bunx baresync generate --config baresync.config.ts
```

The generator produces:
- `local-schema.ts` — `syncOutbox` and `syncCursors` Drizzle table definitions
- `local-synced-schema.ts` — Drizzle table definitions for each synced table (with `localSyncColumns`)
- `migrations.ts` — `EmbeddedMigration` array with `CREATE TABLE` SQL for all tables

You then include the generated migrations in your Rust `lib.rs`:

```rust
// Typically auto-generated or copy-pasted from the TS generator output
builder.migrations(vec![
    EmbeddedMigration { name: "0001_sync_outbox", sql: "CREATE TABLE IF NOT EXISTS sync_outbox (...)" },
    EmbeddedMigration { name: "0002_sync_cursors", sql: "CREATE TABLE IF NOT EXISTS sync_cursors (...)" },
    EmbeddedMigration { name: "0003_items", sql: "CREATE TABLE IF NOT EXISTS items (...)" },
])
```

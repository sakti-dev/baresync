# Migrations

The plugin applies SQL migrations at startup, before any JS code runs. Migrations are embedded into the binary at compile time so the app works offline.

## Migration discovery

### Build script

Write a `build.rs` that reads `.sql` files from your `migrations/` directory and generates a Rust function:

```rust
use std::{env, fmt::Write as _, fs, path::PathBuf};

fn main() {
    generate_migration_manifest();
    tauri_build::build()
}

fn generate_migration_manifest() {
    let manifest_dir =
        PathBuf::from(env::var("CARGO_MANIFEST_DIR").expect("CARGO_MANIFEST_DIR not set"));
    let migration_dir = manifest_dir.join("migrations");
    println!("cargo:rerun-if-changed={}", migration_dir.display());

    let migrations = baresync_core::migrations::collect_migration_files(&migration_dir)
        .expect("failed to discover migrations");

    for migration in &migrations {
        println!("cargo:rerun-if-changed={}", migration.path.display());
    }

    let out_dir = PathBuf::from(env::var("OUT_DIR").expect("OUT_DIR not set"));
    let generated = out_dir.join("my_migrations.rs");

    let mut source = String::new();
    source.push_str(
        "pub fn my_migrations() -> Vec<baresync_core::migrations::EmbeddedMigration> {\n",
    );
    source.push_str("    vec![\n");

    for migration in migrations {
        writeln!(
            source,
            "        baresync_core::migrations::EmbeddedMigration {{ name: {:?}, sql: include_str!(concat!(env!(\"CARGO_MANIFEST_DIR\"), \"/migrations/\", {:?})) }},",
            migration.name,
            migration.file_name
        )
        .expect("failed to write migration manifest");
    }

    source.push_str("    ]\n");
    source.push_str("}\n");

    fs::write(&generated, source).expect("failed to write generated migration manifest");
}
```

This produces `my_migrations()` — a function that returns the embedded migrations.

### Include in lib.rs

```rust
include!(concat!(env!("OUT_DIR"), "/my_migrations.rs"));
```

Then pass the function to the builder:

```rust
.migrations(my_migrations())
```

## Migration files

Place `.sql` files in `src-tauri/migrations/`:

```txt
migrations/
├── 0001_init.sql
├── 0002_add_items.sql
└── 0003_add_stock_counts.sql
```

Files are sorted by filename and applied in order. Only `.sql` files are included.

### Statement breakpoints

Split multiple statements within a single migration using `--> statement-breakpoint`:

```sql
CREATE TABLE locations (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL
);
--> statement-breakpoint
CREATE TABLE items (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  location_id TEXT NOT NULL
);
```

Each segment is executed as a separate statement within a single transaction.

## Migration execution

Migrations run in **strict mode** by default:

- Each migration runs in a transaction
- If any statement fails, the entire migration rolls back
- Already-applied migrations are skipped (tracked by hash in `__drizzle_migrations`)

The plugin calls `run_migrations` during setup, so migrations are applied before your JS code loads.

## Migration tracking

Applied migrations are recorded in `__drizzle_migrations`:

| Column | Type | Description |
|---|---|---|
| `id` | `INTEGER` | Auto-increment primary key |
| `hash` | `TEXT` | Migration name (unique) |
| `created_at` | `INTEGER` | Unix timestamp in milliseconds |

Check migration status from JS:

```ts
const status = await invoke("get_migration_status");
```

## Adding a new migration

1. Create `migrations/0004_add_column.sql` with the new SQL
2. Rebuild — the build script picks it up automatically
3. The plugin applies it on next launch

## Filesystem migrations

If you set `migrations_dir` on the builder, the plugin also reads `.sql` files from that directory at runtime. This is useful for development or dynamic schemas. Embedded migrations run first, then filesystem migrations.

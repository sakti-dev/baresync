# Runtime Tables

Baresync uses three runtime tables that are not synced themselves but support the sync engine. Use the factory functions from `baresync/schema` to create them.

## sync_outbox (local)

Tracks pending local changes that need to be pushed to the server.

| Column | Type | Purpose |
|---|---|---|
| `id` | `text` PK | UUID |
| `table_name` | `text` | Which table the change belongs to |
| `row_id` | `text` | Which row changed |
| `operation` | `text` | `"insert"`, `"update"`, or `"delete"` |
| `payload` | `text` (nullable) | Optional JSON payload |
| `scope_id` | `text` | Scope the change belongs to |
| `changed_at` | `text` | ISO timestamp of the change |
| `synced_at` | `text` (nullable) | When the change was synced (null = pending) |

The table has a unique partial index on `(table_name, row_id) WHERE synced_at IS NULL`. This means only one pending outbox entry per row. When `enqueueChange` is called for a row that already has a pending entry, the existing row is updated (upsert coalescing) instead of causing a constraint violation. The `"insert"` operation is preserved if the existing entry was an insert; `"update"` replaces `"update"`.

This table lives in the **local app database** only.

## sync_cursors (local)

Stores the last cursor timestamp per scope so the client can do incremental pulls.

| Column | Type | Purpose |
|---|---|---|
| `id` | `integer` PK (auto) | Row ID |
| `scope_id` | `text` | Scope identifier |
| `last_cursor` | `text` | Last server watermark |
| `updated_at` | `text` | When the cursor was last updated |

After a successful pull, the sync engine updates `last_cursor` to the highest `sync_updated_at` value from the pulled rows.

This table lives in the **local app database** only.

## sync_batch_requests (server)

Stores idempotency records for push requests on the server.

| Column | Type | Purpose |
|---|---|---|
| `id` | `integer` PK (auto) | Row ID |
| `client_id` | `text` | Client identifier |
| `idempotency_key` | `text` | Unique key per push batch |
| `request_hash` | `text` | Hash of the request body |
| `status` | `text` | `"pending"`, `"completed"`, or `"failed"` |
| `response_body` | `text` (nullable) | Cached response for replay |
| `created_at` | `integer` | Unix timestamp |
| `completed_at` | `integer` (nullable) | When processing finished |

The table has a unique index on `(client_id, idempotency_key)`. If a client retries a push with the same idempotency key, the server returns the cached response instead of processing it again.

This table lives in the **server database** only.

## Factory functions

Baresync provides factory functions that create Drizzle table definitions for the runtime tables. Use these in your sync contract package so both sides get the correct schema.

### createSyncOutboxTable

Creates the `sync_outbox` table with its unique index on pending rows.

```ts
import { createSyncOutboxTable } from "baresync/schema";

export const syncOutbox = createSyncOutboxTable();
```

### createSyncCursorsTable

Creates the `sync_cursors` table.

```ts
import { createSyncCursorsTable } from "baresync/schema";

export const syncCursors = createSyncCursorsTable();
```

### createSyncBatchRequestsTable

Creates the `sync_batch_requests` table with its idempotency index.

```ts
import { createSyncBatchRequestsTable } from "baresync/schema";

export const syncBatchRequests = createSyncBatchRequestsTable();
```

### Typical local-schema.ts

```ts
import { createSyncCursorsTable, createSyncOutboxTable } from "baresync/schema";

export const syncOutbox = createSyncOutboxTable();
export const syncCursors = createSyncCursorsTable();
```

### Typical api-schema.ts

```ts
import { createSyncBatchRequestsTable } from "baresync/schema";

export const syncBatchRequests = createSyncBatchRequestsTable();
```

# Testing Overview

This section is for application teams using Baresync. It focuses on testing your app's integration, not Baresync's internal repository workflow.

Your tests should prove that **your app** uses Baresync correctly:

- frontend code calls the sync client and reacts to sync events
- local writes create the source row and a pending outbox entry
- your backend implements the sync contract your app expects
- your packaged app can run migrations, sync, and preserve local state

Most apps do not need to test Baresync's internal Rust engine. Baresync covers that in its own test suite. Your tests should focus on your app's schema, backend, UI, and runtime wiring.

## Recommended Layers

| Layer | What to test | Good tools |
|---|---|---|
| Frontend tests | Sync client calls, hooks, providers, event bridge, status UI | Vitest, Testing Library |
| Local database tests | App write path inserts domain rows and `sync_outbox` rows | Vitest or bun:test |
| Server contract tests | Push, pull, status, authorization, idempotency, ordering | Vitest or bun:test |
| App smoke tests | Real Tauri app, real SQLite file, real backend, restart persistence | WebdriverIO, Playwright, Maestro, Appium |
| Advanced Rust/plugin tests | Only if you extend Baresync internals or fork the plugin | Rust tests |

The normal path for an app is frontend tests, local database tests, server contract tests, and one small app smoke test. The advanced Rust pages are for customization work, not day-to-day app integration.

## Mock At Boundaries

Baresync is easiest to test when you mock the edge your code owns:

- In frontend tests, mock the Tauri `invoke` function or mock `baresync/tauri`.
- In local database tests, use a real test database and assert source rows plus outbox rows.
- In server tests, send real `Request` objects to your handlers with test auth and test storage.
- In app smoke tests, do not mock Baresync. Launch the real app against a deterministic test backend.

Avoid mocking the sync engine internals from your app tests. If a behavior can be tested by checking your database, backend response, or app UI, test it there.

## What Your App Should Own

Your app tests should cover:

- scope IDs and authorization rules
- table names and column mapping
- local-only columns such as `is_synced`
- outbox creation after local writes
- backend acceptance and rejection behavior
- query invalidation after Baresync events
- app-specific UI states such as "pending", "synced", or "needs baseline"
- database path and app data reset behavior in smoke tests

Your app tests usually should not cover:

- Baresync's internal chunking algorithm
- every possible conflict resolution edge case through UI automation
- Rust polling internals unless you customize them
- Baresync's internal repository workflow

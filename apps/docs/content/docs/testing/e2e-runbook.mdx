# E2E Runbook

This runbook is for testing **your application** after it integrates Baresync.

The goal is not to test Baresync itself. The goal is to prove that your app wiring works end to end:

- your Tauri app registers the plugin correctly
- your migrations create the schema your app expects
- your frontend calls the right IPC commands
- your local SQLite file is readable, writable, and isolated per test run
- your app can pull server data into local state
- your app can create local data and enqueue it for sync
- your app can push local changes to your backend
- accepted local rows become clean locally
- important local state survives an app restart

Good E2E tests should be small and boring. Put sync edge cases in host tests and backend contract tests. Use UI/device tests only to prove the real runtime wiring works.

## Recommended Layers

Do not collapse all sync testing into one UI test. Each layer should own a different risk.

| Layer | Purpose | Typical cadence |
|---|---|---|
| App unit tests | Validate your own UI state, helpers, and domain logic without Tauri | Every commit |
| JS typecheck and lint | Catch wrong imports, API misuse, and broken app types | Every commit |
| Backend contract tests | Prove your sync backend accepts and returns the protocol your app uses | Every commit or before release |
| Desktop smoke test | Prove your real Tauri desktop app can sync through IPC, SQLite, and your UI | Before release |
| Mobile smoke test | Prove packaged mobile runtime, app-private SQLite path, networking, and lifecycle | Before release or platform changes |

Baresync's own repository uses the same shape internally, but your app should use your own schema, backend, app ID, UI selectors, and test runner.

## What Not To Put In UI E2E

UI E2E is expensive and easy to make flaky. Keep it focused on integration confidence.

Do not use desktop or mobile smoke tests for:

- cursor ordering edge cases
- conflict resolution matrices
- idempotency behavior
- chunk sizing and retry behavior
- every table in your app
- detailed protocol validation

Those belong in backend contract tests, host tests, or direct sync-engine tests. Your UI smoke test only needs one or two representative tables that prove the whole path works.

## Deterministic Test Backend

Your E2E tests need a backend that is deterministic and owned by the test runner.

The backend can be your real backend running in a test mode, or a small fixture server that implements the same sync endpoints your app uses. The important part is that it behaves predictably.

Your test backend should provide:

| Capability | Why it matters |
|---|---|
| Reset endpoint | Clears stale state before each run |
| State inspection endpoint | Lets the test assert what the backend received |
| Fixed baseline data | Lets the test prove pull applies server rows |
| Push recording | Lets the test prove local changes reached the backend |
| Same wire format as production | Exercises JSON exactly as your app uses it |

The backend contract test should also confirm that the JSON transport is actually in use.
- the generated artifacts are checked in and regenerated when the schema changes

Example shape:

```txt
POST /__reset
GET  /__state
POST /sync/status
POST /sync/pull
POST /sync/push
```

`/__reset` and `/__state` are test-only endpoints. Do not expose them in production.

### Backend Contract Test

Before launching a desktop or mobile app, test the backend directly over HTTP. This separates backend contract failures from device and WebView failures.

A useful backend contract test should:

1. Start the test backend on a free port.
2. Use an isolated database, often an in-memory database or per-run file.
3. Wait until the backend is ready.
4. Call `POST /__reset`.
5. Assert the initial state contains your expected seed rows.
6. Call `POST /sync/status` with the expected scope and cursor.
7. Assert invalid scopes are rejected.
8. Call `POST /sync/pull` and assert your seed rows are returned.
9. Call `POST /sync/push` with representative local rows.
10. Assert the push response acknowledges the accepted rows.
11. Call `GET /__state` and assert the pushed rows were recorded.
12. Run the same test against every backend scenario your app supports.

The rows should come from your domain. For example, a POS app might use one category and one product. A notes app might use one notebook and one note. Keep it small, but make it real enough to exercise table ordering and foreign keys.

## Run Isolation

Every smoke run must be isolated from previous runs. A stale database can make a broken sync flow look successful.

Use both:

- a fresh local SQLite file or app-data namespace for each run
- a backend reset before each test

One without the other is not enough.

Stale state can hide these bugs:

- old `sync_outbox` rows make manual sync appear to push current data
- old `sync_cursors` skip the baseline pull path
- old local rows make restart persistence pass without current-run writes
- repeated test IDs collide across runs

For desktop tests, derive your app's Baresync database path from a run ID:

```txt
<temp-dir>/<your-app-name>-baresync-<run-id>.db
```

For Android, use an app-private path and create the parent directory before initializing the plugin:

```txt
/data/user/0/<your.app.id>/files/baresync-<run-id>.db
```

On iOS, use an app container path that your Tauri app can write to.

## Desktop Smoke Test

A desktop smoke test should launch your real Tauri desktop app and drive it through the same public surfaces a user exercises.

Use any runner that can control your Tauri app. Common choices are WebdriverIO with `tauri-driver`, Playwright around a dev WebView setup, or another tool already used in your app. The runner choice matters less than the assertions.

### Desktop Setup

Install the tools for your platform:

- Rust toolchain
- Node or Bun, matching your app
- Tauri CLI
- system libraries required by Tauri on your OS
- a browser automation runner
- `tauri-driver` if you use WebDriver

You do not need Nix to test an app that uses Baresync. If your project already uses Nix, it is fine to put these tools in a dev shell. If your team uses macOS, Windows, Linux packages, CI images, or another toolchain manager, use those instead.

### Desktop Runner Responsibilities

The desktop runner should own all processes it depends on:

1. Allocate a free backend port.
2. Start your deterministic test backend.
3. Export the backend URL to the app.
4. Set a unique run ID or database path for the app.
5. Start your frontend dev server if your Tauri config uses one.
6. Build or launch your Tauri app.
7. Start the automation driver.
8. Kill all spawned processes at the end.

Avoid relying on a backend that a developer manually started on `localhost`. That creates stale state, port conflicts, and false passes.

### Desktop Smoke Scenario

Your desktop smoke should be one short scenario:

1. Launch the app.
2. Wait until the app reports it is ready.
3. Assert migrations ran.
4. Assert the app is using the expected database path or run ID.
5. Assert the app is using the expected sync transport, if your UI exposes it.
6. Trigger baseline sync.
7. Wait until known server rows appear in the UI or local state.
8. Create a representative local row through the app UI.
9. Assert the local row appears before sync.
10. Assert there is a pending local change, either through UI state or SQLite inspection.
11. Trigger manual sync.
12. Assert the backend recorded the pushed row.
13. Assert the accepted local row is clean, for example `is_synced = 1`.
14. Restart the app.
15. Wait for readiness again.
16. Assert the local row and clean state survived restart.
17. Assert the dirty count is zero after restart.

If your app does not expose internal sync state in the UI, add test-only diagnostics behind a non-production flag, or inspect the isolated SQLite file from the test process.

Prefer wire evidence over helper assertions. The useful proof is that the backend recorded the expected JSON requests and the app still passes the same visible sync checks as any other run.

## Mobile Smoke Test

Mobile smoke tests should be even smaller than desktop smoke tests. Their job is lifecycle and packaging confidence:

- the packaged app launches
- the plugin initializes on the device
- the app uses an app-private SQLite path
- the device can reach the test backend
- baseline pull works
- one local write can be pushed
- accepted rows become clean
- data survives kill and relaunch

Use the mobile automation tool that fits your app. Maestro is a good fit for simple Android smoke flows. Appium is also common. Use your existing mobile test stack if you already have one.

### Android Setup

For Android, make sure:

- `adb devices` shows a usable emulator or physical device
- the test APK is installed on the selected target
- the backend URL is reachable from that target
- the Baresync database path is under the app-private files directory

Backend URLs differ by target:

| Target | Backend URL |
|---|---|
| Android emulator | `http://10.0.2.2:<port>` |
| Physical Android device | LAN-reachable host IP, for example `http://192.168.1.50:<port>` |

The backend URL must be available to the app at startup. For mobile builds, that often means compiling it into a test build or passing it through your app's runtime configuration.

### Android Scenario

A useful Android smoke should:

1. Clear app data or install a fresh build, depending on the lifecycle you are testing.
2. Launch the app.
3. Wait for your app's ready text.
4. Trigger baseline sync.
5. Assert server rows are visible.
6. Create one local row.
7. Assert the local row is visible before sync.
8. Trigger manual sync.
9. Wait until the row is clean.
10. Kill and relaunch the app.
11. Assert the local row and clean state persisted.
12. Assert the backend recorded the pushed row from the same backend URL the app used.

Android selectors often need more patience than desktop selectors. Prefer semantic waits over fixed sleeps.

For example, with Maestro:

```yaml
- extendedWaitUntil:
    visible: ".*Your synced row label.*"
    timeout: 30000
```

If your app renders JSON text for diagnostics, remember that SQLite booleans often appear as `1` or `0`, not `true` or `false`.

## Good Waits

Most flaky E2E tests come from weak waits.

Wait for semantic state:

```ts
await waitForText("#app-status", "ready", "app should be ready");
await waitForTextIncludes("#sync-result", "manual:", "manual sync should finish");
await waitForTextMatches("#rows", CLEAN_LOCAL_ROW_RE, "local row should be clean");
```

Avoid timing guesses:

```ts
await sleep(5000);
expect(await text("#app-status")).toBe("ready");
```

Good wait targets include:

- app readiness flag
- migration count
- database path or run ID
- baseline sync result
- manual sync result
- expected server row visible locally
- expected local row visible before sync
- expected clean state after sync
- dirty count after sync

## Required Assertions

At minimum, your Baresync E2E smoke should assert both server-side and local-side state.

Server-side assertions:

- the backend starts in a known state
- baseline data exists before sync
- pushed local row IDs are recorded after manual sync
- the test reads backend state from the same URL the app used

Local-side assertions:

- migrations ran
- baseline rows exist locally after pull
- local writes create pending outbox entries
- accepted local rows become clean
- dirty count returns to zero
- clean state survives app restart

Backend acceptance alone is not enough. A backend can accept a push while the local database still thinks the row is dirty.

## Debugging Sequence

When a smoke test fails, debug in this order:

1. Confirm the backend is running and responds to its state endpoint.
2. Confirm the app received the same backend URL the test is inspecting.
3. Confirm the app is using a fresh local database path.
4. Confirm the app reached readiness before the test clicked anything.
5. Confirm migrations ran.
6. Confirm baseline pull returned rows from the backend.
7. Confirm local create wrote the source table row.
8. Confirm local create wrote a pending `sync_outbox` row.
9. Confirm manual sync sent the push payload.
10. Confirm the backend recorded the pushed row.
11. Confirm accepted outbox rows were marked synced.
12. Confirm accepted source rows were marked clean.
13. Confirm restart uses the same expected database path.

If the failure is protocol-level, move it out of UI E2E and reproduce it in a backend contract or host test.

## Common Failures

### The app cannot reach localhost

On desktop, this usually means your frontend dev server or backend is not running, or the app launched before it was ready.

On Android, `localhost` means the device itself, not your development machine. Use `10.0.2.2` for Android emulator access to the host, or a LAN-reachable IP for a physical device.

### Manual sync returns no synced tables

The push engine probably found no pending local changes.

Inspect your local database:

```sql
SELECT id, table_name, row_id, scope_id, synced_at
FROM sync_outbox;
```

Check that:

- `scope_id` matches the sync client scope
- `synced_at` is `NULL` before manual sync
- `table_name` matches the sync contract table name exactly
- `row_id` matches the source table primary key
- the source row exists

### Backend did not record pushed rows

Common causes:

- the app used a different backend URL than the test inspected
- the backend reset happened after the push
- manual sync did not complete before the assertion
- the pushed row used a different scope than the backend expected

Assert the manual sync result before checking backend state.

### Local row stays dirty after successful push

Common causes:

- accepted outbox rows were not marked synced
- source rows were marked clean before outbox entries were cleared
- clean-marking query skips rows that still have pending outbox entries
- backend response did not acknowledge the row ID you expected

Expected behavior:

1. Backend accepts the pushed row.
2. Accepted outbox entries are marked synced.
3. Accepted source rows are marked clean.
4. Dirty count returns to zero.

### App launches but never becomes ready

Likely causes:

- plugin command registration mismatch
- frontend calls a different command name than Rust registered
- migrations failed
- database path is not writable
- frontend bundle failed before app bootstrap
- backend URL is missing or invalid and startup code does not handle it

Check app logs before treating this as a sync-engine failure.

## Platform Notes

Use whatever toolchain is normal for your app and CI.

For desktop Tauri tests:

- macOS needs the normal Xcode command line tooling and Tauri prerequisites.
- Windows needs the Microsoft C++ build tools and WebView2.
- Linux needs the Tauri host libraries for your distribution, including WebKit and GTK-related packages.

For mobile tests:

- Android needs Android SDK, NDK if your Tauri setup requires it, `adb`, and a connected target.
- iOS needs Xcode and a simulator or device setup supported by your app.

Baresync does not require Nix. The Baresync repository uses Nix for its own contributor environment, but public apps can use any reproducible setup.

## Reference: Baresync's Own Fixture

Baresync's repository includes a public fixture app that applies this pattern to a tiny category/product schema. Treat it as an example, not as something your app must copy.

The fixture demonstrates:

- a deterministic test backend
- JSON transport mode
- a Tauri fixture app using real plugin registration
- embedded migrations
- frontend `invoke` calls
- Drizzle over Tauri IPC
- desktop smoke with WebdriverIO and `tauri-driver`
- Android smoke with Maestro

Your app should keep the same testing principles, but replace the fixture schema, seed data, UI selectors, app ID, backend URL, and commands with your own.

## Done Means

Before you trust an E2E change, collect evidence:

- backend contract tests pass for the wire format your app uses
- desktop smoke passes on the platform you support
- mobile smoke passes on a real target or emulator when mobile is in scope
- test logs show the backend URL, run ID, and database path used
- backend state confirms pushed rows
- local state confirms accepted rows are clean
- app restart proves persistence

If a platform could not be tested because no device, emulator, or CI runner was available, say that explicitly. Do not count an unrun smoke test as passing.

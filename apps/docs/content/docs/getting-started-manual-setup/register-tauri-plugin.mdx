# Register the Tauri Plugin

The Baresync Tauri plugin owns the local SQLite database, runs migrations, and exposes commands through the standard Tauri plugin namespace:

```txt
plugin:baresync|run_sql
plugin:baresync|sync_now
plugin:baresync|get_polling_status
```

You normally do not register Baresync commands in your app's `generate_handler!` macro. The plugin registers its own IPC handlers.

## Add Rust dependencies

Edit `apps/app/src-tauri/Cargo.toml`:

```toml
[dependencies]
baresync-core = { version = "0.1.0" }
tauri = { version = "2", features = [] }
tauri-plugin-baresync = { version = "0.1.0" }
```

## Configure the plugin

Create or update `apps/app/src-tauri/src/lib.rs`:

```rust
use tauri_plugin_baresync::builder::Builder as BaresyncBuilder;

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .plugin(
            BaresyncBuilder::new()
                .api_base_url("http://127.0.0.1:3001")
                .db_name("baresync.db")
                .contract_json(include_str!(
                    "../../../../packages/sync-contract/generated/sync-contract.json"
                ))
                .migrations_path("migrations")
                .poll_interval_secs(30)
                .build(),
        )
        .run(tauri::generate_context!())
        .expect("failed to run app");
}
```

## Where generated metadata comes from

The plugin expects the generated sync contract metadata that Baresync writes from your `sync-contract` package. Use `contract_json(...)` to avoid duplicating table ordering and local-only column metadata in Rust.

If you already have explicit `SyncContractTables` in a test or specialized setup, `contract_tables(...)` still works.

## Migrations

The plugin can load SQL migrations from `migrations_path(...)`, or you can embed them with `migrations(...)`. For the standard setup, keep your migration files in `apps/app/src-tauri/migrations/` and let the plugin load them from there.

## Command registration

Your app can still define its own commands for app-specific behavior, such as reset or debug helpers. Those commands are separate from Baresync and belong in your app's own `generate_handler!` macro.

The Baresync commands themselves are already available through the plugin namespace, so the frontend calls the following directly:

```ts
await invoke("plugin:baresync|run_migrations");
await invoke("plugin:baresync|run_sql", { query });
await invoke("plugin:baresync|sync_now", { scopeId: "merchant-1" });
```

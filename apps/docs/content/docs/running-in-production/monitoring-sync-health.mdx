# Monitoring Sync Health

Sync works best when you can see what it's doing. This page covers the APIs for checking sync state and how to present them to users.

## The three health metrics

Every sync cycle produces three numbers that tell you everything:

### Dirty count

```ts
const state = await client.getState();
console.log(state.local_dirty_count); // number of unsynced changes
```

| Value | Meaning |
|---|---|
| `0` | All local changes have been pushed and confirmed. |
| `> 0` | There are pending changes in the outbox waiting to be pushed. |

A non-zero dirty count is **normal** between sync cycles. If it stays non-zero for minutes after a sync, something is wrong (see [Troubleshooting](/docs/running-in-production/troubleshooting)).

### Last server watermark

```ts
const state = await client.getState();
console.log(state.last_server_watermark); // e.g. "sync:1747894800000:categories:cat-1"
```

| Value | Meaning |
|---|---|
| `""` (empty) | Never synced, or cursor was reset. `needs_baseline_sync` will be `true`. |
| Non-empty string | Last cursor saved after a successful pull. |

The watermark format is `sync:{timestamp}:{table}:{rowId}`. It tells the server "I have everything up to this point." A stale watermark means the client hasn't pulled in a while.

### Needs baseline sync

```ts
const state = await client.getState();
console.log(state.needs_baseline_sync); // true = needs full pull
```

| Value | Meaning |
|---|---|
| `true` | No cursor exists. The next sync will pull all data from scratch. |
| `false` | Cursor exists. Incremental sync will only pull changes since the cursor. |

This is `true` on first launch and after a [full reset](/docs/running-in-production/resetting-local-db). If it's `true` after you've already synced, the cursor wasn't saved — check DB write permissions.

## Polling status

If you're using auto-polling, check whether the loop is running:

```ts
const pollStatus = await client.getPollingStatus();
console.log(pollStatus.running); // boolean
console.log(pollStatus.paused);  // boolean
console.log(pollStatus.last_sync_at); // timestamp or null
```

| Scenario | `running` | `paused` | Action |
|---|---|---|---|
| Normal operation | `true` | `false` | None |
| Window unfocused, `poll_on_background = false` | `true` | `true` | Normal — resumes when focused |
| Never started or stopped | `false` | `false` | Call `client.startPolling()` |
| App crashed and restarted | `false` | `false` | Start polling again on app init |

## Database info

Check the SQLite database file size and path:

```ts
const dbInfo = await invoke("plugin:baresync|get_db_info");
console.log(dbInfo.db_path);        // "/data/user/0/.../baresync.db"
console.log(dbInfo.size_bytes);     // 1048576
console.log(dbInfo.size_formatted); // "1.00 MB"
```

Use this to detect unexpected DB growth. If the file keeps growing even when sync is idle, you may have un purged outbox entries or soft-deleted rows accumulating.

## Building a sync status indicator

Here's a React component that shows sync health in your UI:

```tsx
import type { SyncClient } from "baresync/tauri";
import { useEffect, useState } from "react";

type SyncHealth = "synced" | "pending" | "offline" | "error";

function useSyncHealth(client: SyncClient, intervalMs = 5000) {
  const [health, setHealth] = useState<SyncHealth>("synced");
  const [dirtyCount, setDirtyCount] = useState(0);

  useEffect(() => {
    let mounted = true;

    async function check() {
      try {
        const state = await client.getState();
        if (!mounted) return;
        setDirtyCount(state.local_dirty_count);

        if (state.local_dirty_count === 0) {
          setHealth("synced");
        } else {
          setHealth("pending");
        }
      } catch {
        if (mounted) setHealth("error");
      }
    }

    check();
    const id = setInterval(check, intervalMs);
    return () => {
      mounted = false;
      clearInterval(id);
    };
  }, [client, intervalMs]);

  return { health, dirtyCount };
}

function SyncIndicator({ client }: { client: SyncClient }) {
  const { health, dirtyCount } = useSyncHealth(client);

  const label = {
    synced: "All changes saved",
    pending: `${dirtyCount} unsynced`,
    offline: "Offline",
    error: "Sync error",
  }[health];

  const color = {
    synced: "green",
    pending: "orange",
    offline: "gray",
    error: "red",
  }[health];

  return (
    <span style={{ color }} aria-live="polite">
      {label}
    </span>
  );
}
```

## What to log

For production debugging, log these events:

| Event | What to log | Why |
|---|---|---|
| Sync cycle completes | `getState()` result, `syncNow()` return value | Track sync frequency and catch anomalies |
| Dirty count stuck > 5 minutes | `local_dirty_count`, `last_server_watermark` | Detect stuck pushes early |
| Polling stops unexpectedly | `getPollingStatus()` result | Catch lifecycle bugs |
| DB size exceeds threshold | `get_db_info()` result | Catch data accumulation issues |

Don't log the full sync payload — it contains user data. Log metadata (counts, timestamps, status codes) only.

## Interpreting the numbers

### Healthy baseline

```txt
dirty_count:       0
watermark:         "sync:1747894800000:products:prod-42"
needs_baseline:    false
polling running:   true
polling paused:    false
last_sync_at:      "2026-05-22T10:30:00Z"
db size:           ~2 MB
```

### After user creates a row (before next sync)

```txt
dirty_count:       1         ← new row is pending
watermark:         unchanged
needs_baseline:    false
```

Normal. The next polling tick or `syncNow()` call will push it.

### After network outage (polling active)

```txt
dirty_count:       15        ← accumulated during outage
watermark:         stale     ← hasn't advanced
needs_baseline:    false
polling running:   true
polling paused:    false
last_sync_at:      old       ← last successful sync was before outage
```

Normal during outage. The polling loop silently retries. Dirty count decreases as sync succeeds after connectivity returns.

### Something is wrong

```txt
dirty_count:       42        ← never decreasing
watermark:         "sync:..." ← advancing (pull works)
needs_baseline:    false
polling running:   true
last_sync_at:      recent    ← sync cycles are completing
```

Pull works but push doesn't. Check server logs for push rejection (409, 413, or 500). See [Troubleshooting](/docs/running-in-production/troubleshooting).

# Configuration

Baresync has two layers of configuration: the **Tauri plugin** (controls runtime behavior on the client) and the **server** (controls push limits and response behavior). This page covers every setting you can change, what the defaults are, and when to deviate from them.

## Plugin builder options

When you register the plugin in your Tauri app's `main.rs`, you use the builder pattern. Every option has a sensible default, so most apps only set a few:

```rust
use tauri_plugin_baresync::builder::Builder as BaresyncBuilder;

tauri::Builder::default()
    .plugin(
BaresyncBuilder::new()
    .api_base_url("https://api.example.com")
    .db_path("baresync.db")
    .poll_interval_secs(30)
    .migrations_path("migrations")
    .contract_tables(tables)
    .build(),
)
```

### All options

| Method | Type | Default | Purpose |
|---|---|---|---|
| `.api_base_url(url)` | `String` | `""` (required) | Your sync server's base URL. All sync endpoints are relative to this. |
| `.db_path(path)` | `String` | `"baresync.db"` | Database file path. Relative paths resolve under the app data directory; absolute paths are used as-is. |
| `.contract_tables(tables)` | `SyncContractTables` | empty | Table ordering metadata from your generated artifacts. |
| `.contract_json(json)` | `String` | `None` | Alternative to `contract_tables` — pass the generated contract JSON string directly. |
| `.migrations(migs)` | `Vec<EmbeddedMigration>` | `[]` | Embedded SQL migrations. Use this or `.migrations_path()`, not both. |
| `.migrations_path(path)` | `PathBuf` | `None` | Path to `.sql` migration files. Relative paths resolve from Tauri resources. |
| `.encryption_key_provider(p)` | `impl EncryptionKeyProvider` | `None` | Custom encryption key provider for encrypted SQLite databases. |
| `.poll_interval_secs(secs)` | `u64` | `30` | How often the polling loop checks for changes after your app calls `startPolling()`. Do not call `startPolling()` if your app is manual-sync only. |
| `.poll_on_background(bool)` | `bool` | `false` | Whether to keep polling when the window is unfocused. `false` saves battery on mobile. |

## Server configuration

If you use Baresync's server handler helpers, the push handler validates incoming requests with Baresync's default API limits: 2 MB per push body and 2000 total rows per push.

```ts
import { createSyncPushHandler } from "baresync/server";

const pushHandler = createSyncPushHandler({
  applyPushChanges,
  idempotency: { db },
  resolveScope,
  upsertOrder: ["categories", "products"],
});
```

If you build your own server pipeline, use `validatePushEnvelope()` and pass the limits explicitly:

```ts
import { decodeSyncRequest, validatePushEnvelope } from "baresync/server";

const decoded = await decodeSyncRequest({
  kind: "push",
  request,
});

validatePushEnvelope(decoded, {
  maxBytes: 2 * 1024 * 1024,
  maxRows: 2000,
});
```

### Recommended server limits

| Setting | Default | Purpose |
|---|---|---|
| `maxBytes` | 2 MB | Maximum push body size. Rejects with `413` if exceeded. |
| `maxRows` | 2000 | Maximum total rows in a push. Rejects with `413` if exceeded. |

The defaults are intentionally conservative: 256 KB client target and 2 MB server max. The client adapts via 413 split-retry if the server has stricter limits.

## Environment-specific settings

### Development

```rust
BaresyncBuilder::new()
    .api_base_url("http://localhost:3000")
    .db_path(":memory:")  // fresh DB on every restart
    .migrations_path("migrations")
    .poll_interval_secs(10)  // fast feedback loop
    .poll_on_background(true)  // don't pause when you switch to the terminal
```

### Production

```rust
BaresyncBuilder::new()
    .api_base_url("https://api.example.com")
    .db_path("baresync.db")
    .migrations_path("migrations")
    .poll_interval_secs(30)
    .poll_on_background(false)  // save battery on mobile
```

### Testing

```rust
BaresyncBuilder::new()
    .api_base_url("http://localhost:3001")
    .db_path(":memory:")
    .poll_interval_secs(30) // only used if your test calls startPolling()
```

For testing sync behavior, use the core engine directly with a custom transport if needed.

## JS client configuration

When you create a `SyncClient` in your frontend, you set the scope and (optionally) a custom invoke:

```ts
import { invoke } from "@tauri-apps/api/core";
import { createSyncClient } from "baresync/tauri";

const client = createSyncClient({
  scopeId: "merchant-123",
  invoke,
});
```

| Field | Required | Purpose |
|---|---|---|
| `scopeId` | Yes | The sync scope for this client. Determines which data is synced. |
| `invoke` | No | Custom invoke function. Only useful for testing. |

## Common mistakes

**Polling too fast** — `poll_interval_secs(1)` creates unnecessary load. 30 seconds is a good default. If you need faster updates, consider a push notification that calls `syncNow()` instead.

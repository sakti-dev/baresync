# Troubleshooting First Run

## The app says "failed to run inventory app"

Check that your `lib.rs` compiles. The most common cause is a mismatched `baresync-core` or `tauri-plugin-baresync` path in `Cargo.toml`.

```bash
cd apps/app/src-tauri
cargo check
```

## The server does not start

The scaffold creates `apps/server/data/` at scaffold time. If you cloned the example or moved the project, make sure the database directory exists and is writable. You can also override the path via the `<PROJECT_NAME>_SERVER_DB_PATH` environment variable:

```bash
MY_APP_SERVER_DB_PATH=/tmp/my-app.db bun run dev
```

If you are using Drizzle migrations on the server, make sure you have generated them:

```bash
cd apps/server
bun run db:generate
```

## No data appears in the app

1. **Is the server running?** Check `http://127.0.0.1:3001/health`.
2. **Is there data on the server?** Seed the server database.
3. **Did polling start?** Open the Tauri devtools console and look for sync logs.
4. **Are your query keys correct?** React Query caches are keyed by the array you pass to `useDrizzleQuery`. The invalidation in `SyncClientProvider` must match.

## Sync is silently not working (no errors in logs)

The Baresync Rust plugin logs sync activity using the `log` crate. If you see no `[baresync]` messages in your terminal, your app is missing a logging frontend. Add `env_logger` to your app's `Cargo.toml`:

```toml
[dependencies]
env_logger = "0.11"
```

Then initialize it before building the Tauri app in `src-tauri/src/lib.rs`:

```rust
#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    env_logger::Builder::from_env(env_logger::Env::default().default_filter_or("info"))
        .init();
    tauri::Builder::default()
        // ...
}
```

Run your app with `RUST_LOG=debug` to see HTTP requests and sync engine decisions:

```bash
RUST_LOG=debug bun run dev
```

Common log messages to look for:

- `[baresync] plugin setup: api_url=...` — confirms the plugin loaded with the right config
- `[baresync] contract tables: upsert_order=[...]` — confirms contract was parsed (empty arrays = no tables synced)
- `[baresync] HTTP POST ... -> 404` — server URL mismatch (check `api_base_url` matches your server routes)
- `[baresync] polling sync_fn failed` — a sync cycle failed with an error

## Sync outbox is not draining

1. Check that your `contract_tables` in `lib.rs` has the correct upsert and delete order.
2. Check that the server `/sync/push` route returns 200.
3. Check the server console for errors in `applyPushChanges`.

## "table not found" errors

Make sure your migration SQL includes all synced tables plus `sync_outbox` and `sync_cursors`. If you add a new table, create a new migration file (e.g., `0002_add_notes.sql`) and rebuild the Tauri app. The plugin will apply pending migrations on next startup.

## Build script does not find migrations

Make sure the `.sql` files are in `apps/app/src-tauri/migrations/` and that `build.rs` points at that directory. Run `cargo clean` and rebuild if you suspect stale build artifacts.

## Multiple outbox entries for the same row

The `sync_outbox` table has a unique index on `(table_name, row_id)` where `synced_at IS NULL`. Calling `writeLocalChange` for the same row twice within one scope will upsert the outbox entry rather than create duplicates. If you see duplicates, check that your migration created the index correctly.

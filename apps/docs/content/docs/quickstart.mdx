This guide follows the same shape as the inventory example in this repository: define local and API synced schemas, create a generator config, generate artifacts, register the Tauri plugin, access SQLite through the plugin, and call sync commands from the frontend.

For a full runnable starter, use [`examples/inventory`](https://github.com/sakti-dev/baresync/tree/main/examples/inventory). It is the canonical fullstack example for new users.

That starter keeps both the primitive and Drizzle helper-backed server repository paths in the inventory server so you can compare the sync plumbing side by side.

## Install

Inside this repo, the package is already available through the workspace. A consumer app will eventually install the public package and the Rust plugin crate:

```bash
bun add baresync
```

## Define synced tables

Baresync expects synced tables to use a single text `id` primary key and sync columns. Local tables use `localSyncColumns()`.

```ts
import { localSyncColumns } from "baresync/schema";
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const categories = sqliteTable("categories", {
  id: text("id").primaryKey(),
  merchantId: text("merchant_id").notNull(),
  name: text("name").notNull(),
  sortOrder: integer("sort_order").notNull().default(0),
  ...localSyncColumns(),
});

export const products = sqliteTable("products", {
  id: text("id").primaryKey(),
  merchantId: text("merchant_id").notNull(),
  categoryId: text("category_id").notNull().references(() => categories.id),
  name: text("name").notNull(),
  priceMinorUnits: integer("price_minor_units").notNull(),
  ...localSyncColumns(),
});
```

The API schema uses the same replicated tables plus server-side sync columns.

```ts
import { apiSyncColumns } from "baresync/schema";
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const categories = sqliteTable("categories", {
  id: text("id").primaryKey(),
  merchantId: text("merchant_id").notNull(),
  name: text("name").notNull(),
  sortOrder: integer("sort_order").notNull().default(0),
  ...apiSyncColumns(),
});

export const products = sqliteTable("products", {
  id: text("id").primaryKey(),
  merchantId: text("merchant_id").notNull(),
  categoryId: text("category_id").notNull().references(() => categories.id),
  name: text("name").notNull(),
  priceMinorUnits: integer("price_minor_units").notNull(),
  ...apiSyncColumns(),
});
```

## Create the sync config

Group both synced schema views in `sync.config.ts`:

```ts title="sync.config.ts"
import { defineProtobufSyncConfig, defineSyncConfig } from "baresync/generator";
import * as apiSyncedSchema from "./src/api-synced-schema";
import * as localSyncedSchema from "./src/local-synced-schema";

export const syncGeneratorConfig = defineSyncConfig({
  apiSyncedSchema,
  localSyncedSchema,
  outputDir: "./generated",
  packageName: "example.sync.v1",
  tables: {
    categories: { scope: "merchant_id" },
    products: { scope: "merchant_id" },
  },
});

export const protobufSyncGeneratorConfig = defineProtobufSyncConfig({
  apiSyncedSchema,
  localSyncedSchema,
  outputDir: "./generated/protobuf",
  outputs: {
    proto: "./generated/protobuf/sync.proto",
    runtimeSourceTs: "./generated/protobuf/runtime.ts",
    runtimeTs: "./generated/protobuf/runtime.generated.ts",
    rustSyncMappers: "../../apps/app/src-tauri/src/protobuf_generated.rs",
    syncTs: "./generated/protobuf/sync.generated.ts",
  },
  packageName: "example.sync.v1",
  tables: {
    categories: { scope: "merchant_id" },
    products: { scope: "merchant_id" },
  },
});
```

The scope column decides which merchant, outlet, workspace, user sandbox, or other app-owned boundary a row belongs to.

The generator checks this config before writing files. It reports errors for missing primary keys, missing sync columns, duplicate table names, unsupported primary keys, required foreign keys to non-synced tables, FK cycles, and unexpected drift between local/API schema views.

## Generate runtime artifacts

Run the generator from the directory that contains `sync.config.ts`:

```bash
bunx baresync doctor
bunx baresync generate
```

By default, generation writes to `./generated`. The core outputs are `sync-contract.json`, `sync-table-order.ts`, and `sync-contract.manifest.json`.

## Register the Tauri plugin

The plugin owns the SQLite pool, migrations, sync config, and contract table metadata.

```rust
use tauri_plugin_baresync::builder::Builder as BaresyncBuilder;

fn sync_tables() -> baresync_core::engine::SyncContractTables {
    baresync_core::engine::SyncContractTables {
        upsert_order: vec!["categories".into(), "products".into()],
        delete_order: vec!["products".into(), "categories".into()],
        local_only_columns: vec!["is_synced".into()],
    }
}

tauri::Builder::default()
    .plugin(
        BaresyncBuilder::new()
            .api_base_url("https://api.example.com")
            .encoding("json")
            .db_path("baresync.db")
            .contract_tables(sync_tables())
            .build(),
    );
```

The fixture app uses explicit contract table metadata today. Generated Rust table metadata can replace the handwritten values as the generator surface settles.

## Query SQLite from the app

Use the Drizzle proxy helper so the frontend and sync engine talk to the same plugin-owned SQLite database.

```ts
import { createTauriDrizzleDatabase } from "baresync/db";
import { invoke } from "@tauri-apps/api/core";
import { categories, products } from "./schema";

export const db = createTauriDrizzleDatabase({
  schema: { categories, products },
  invoke,
});
```

The helper maps Drizzle proxy calls to the plugin commands `run_sql` and `run_sql_batch`.

## Run sync from the frontend

Create a client with a stable `scopeId` and call the sync commands. The current JS client passes `scopeId` to the Tauri commands; the plugin registration owns API URL and encoding.

```ts
import { createSyncClient } from "baresync/tauri";
import { invoke } from "@tauri-apps/api/core";

const sync = createSyncClient({
  apiUrl: "https://api.example.com",
  encoding: "json",
  scopeId: "merchant-1",
  invoke,
});

await sync.syncNow();

const state = await sync.getState();
```

The available commands are `syncNow`, `push`, `pull`, `fullResync`, and `getState`.

## What happened

`syncNow` asks the server status endpoint whether there are remote changes, checks the local outbox state, chooses the smallest useful mode, and then runs pull and/or push through the Rust engine. Pull applies rows in generated upsert order and deletions in reverse order. Push reads pending outbox rows, chunks by row and byte limits, sends idempotent batches, clears accepted rows, and baseline-pulls rejected tables when the server wins.
